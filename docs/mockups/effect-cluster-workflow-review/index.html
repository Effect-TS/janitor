01 / Architecture

How Janitor runs background work

Start with the job Janitor has to do

Consider a repository with a rule that adds a release label when a pull request contains an added changeset file and is no longer a draft. Janitor has to notice a relevant change, establish the current PR state, evaluate the configured policy, and make the label on GitHub agree with that decision. The browser also needs to show the repository, its configuration, and the progress of background work.

Each part can finish at a different time. GitHub can deliver an event twice or after a newer event. Fetching a PR and its files takes several requests. GitHub can ask the application to wait for API budget. A deployment can replace the process halfway through the work. A person can publish a different rule while the old evaluation is running.

The architecture separates work that must survive those interruptions from work that can be repeated. It records the accepted event, coordinates which refresh owns a target, checkpoints expensive steps, and records the decision and its label actions. There is no single transaction that covers Cloudflare, PostgreSQL, and GitHub. Most of the design follows from that constraint.

What is authoritative, and what can lag

GitHub is authoritative for PRs, issues, labels, and repository access. PostgreSQL is authoritative for Janitor configuration and for Janitor's account of what it has observed or attempted. A workflow checkpoint answers which steps an execution has recorded. It does not prove that the PR is still unchanged on GitHub.

The GitHub mirror is a local read model: tables arranged so the application can query repository data without making a GitHub request for every screen. This saves API budget and lets reads continue while synchronization is delayed. The cost is staleness. Janitor therefore tracks verification and pending work separately from the data itself. A row can be visible before it is fresh enough to authorize a label change. [63][64]

How to read the explanations

Implementation statements are grounded in the cited source. Explanations of what a mechanism protects are reasoning from that code. Where the repository records a design decision or an experiment, it is named explicitly. The review does not claim that the chosen provider or runtime was proven better than every alternative.

Janitor has a browser application, an API Worker, and durable background executions. Effect describes the services and workflow steps. A vendored Cloudflare adapter maps those executions onto SQLite-backed Durable Objects. PostgreSQL stores the GitHub mirror, configuration, coordination records, and a transactional outbox that requests workflow execution.

The useful distinction is acceptance, execution, and business completion. A webhook can be accepted into a queue before PostgreSQL sees it. An outbox request can be accepted by the workflow engine before its work finishes. A reconciliation can be recorded as evaluated even when its label writes later fail. Each stage has its own status and recovery rules.

The website owns the custom domain. The more specific /api/v1/* route goes to ClusterWorker. Human API requests verify Cloudflare Access assertions; webhook ingress uses GitHub signature verification. All workflow handlers, the queue consumer, and the API ship in the same backend deployment.

Three kinds of process have different lifetimes

A Worker invocation handles an HTTP request, queue delivery, or cron event. Its JavaScript isolate can be reused, but its memory is not durable. An Effect fiber is a running computation inside that process. Forking a fiber can let a request return sooner; it does not, by itself, preserve the computation after the process disappears.

A Durable Object gives a stable address and storage to a particular object. This adapter uses a distinct object for each workflow execution, so its checkpoint writes are local to that execution. Many executions can run in different objects at the same time. Sharing a Worker deployment does not make the entire backend one serial process.

PostgreSQL coordinates facts that cross execution boundaries. Two workflow objects can both act on one repository, but they consult the same sync targets, rate budget, and configuration records. Object-local serialization cannot enforce those repository-wide rules by itself. [65][27]

The deployment split follows different responsibilities

The website Worker owns the frontend build and static assets. ClusterWorker owns the backend entrypoints and the Durable Object classes. The topology notes record that a proposed forwarding Worker and service binding were replaced with a more specific API route on the same hostname. Cloudflare routes the request before application code runs. The browser retains one origin for the page and API, while the frontend build stays separate from backend execution. [66]

Keeping ingress, the consumer, and workflow registrations in one backend deployment lets them share schemas and service wiring without an extra application-level HTTP service between them. It also couples their releases. A backend deployment can change the code used to resume an old workflow, so deployment compatibility matters even when no new request is being accepted. This is a tradeoff of the implemented topology, not a claim that separate services could never work.

02 / Request lifecycle

From an event to a label

Projection is the inexpensive database step. Refresh is the GitHub-reading step. Keeping them separate allows the application to record what arrived without making event acceptance wait for pagination, API budget, or AI classification. It also gives each failure a clear location: accepted delivery, failed projection, blocked refresh, or failed label write. [67][68]

A webhook describes an observation at one moment. A labeling rule may need details the payload does not contain, such as all changed files or current reviews. Even a complete payload can be old by the time it is consumed. Janitor first projects supported observations into the mirror, then uses a targeted refresh to establish the data required for evaluation.

The event is a reason to check, not a complete decision input

Ingress caps bodies at 1 MiB. Oversized, unsupported, or non-JSON deliveries are intentionally acknowledged and dropped. Invalid signatures receive 401. Supported payloads are encrypted; ciphertext up to 64 KiB travels inline, larger ciphertext goes into R2. A successful enqueue returns 202. Storage or enqueue failure returns 503. [9]

The consumer resolves any R2 payload and calls GitHubWebhookJournal.record. Delivery ID uniqueness makes journal insertion idempotent. The delivery and projection outbox request share a PostgreSQL transaction. After commit, it acknowledges the queue message and attempts immediate dispatch. R2 deletion is best effort. [10]

pull_request Update the mirror. If the repository is enabled, invalidate its targeted entity refresh.
pull_request_review, check_run, check_suite, status Accepted and decoded, but applyEvent falls through without invalidating a target.

Four identifiers answer four different questions

deliveryId asks whether this webhook has been received already. A journal sequence orders observations within Janitor. A sync generation identifies requested and verified work for one target. A rules revision identifies the configuration used to evaluate it. Reusing one identifier for all four purposes would lose information: several deliveries can share a refresh, and the same verified PR can need evaluation under a newer revision.

Workflow execution IDs add an execution-level identity. They are derived from a stable tag and the workflow's idempotency input. The outbox stores a readable business key for dispatch, while the engine derives its own ID. These identifiers connect the records; they do not imply that every delivery creates exactly one GitHub request. [14][69]

A workflow is a finite unit of recoverable work

Discovery, inventory, track scans, and entity refreshes operate at different scopes. An installation can have many repositories; a repository can have many issues. Splitting those scopes lets an entity refresh make progress without waiting for an unrelated full inventory scan. A failed PR refresh also does not require rerunning the entire application inventory.

A separate reconciliation execution identifies the exact snapshot generation and rules revision being considered. A separate test execution gives the UI a job ID immediately and a result it can poll. These boundaries add dispatch and storage overhead, but they make retry scope, status, and deduplication specific to the operation. They are not one long workflow that blocks while all descendants finish.

Downstream work is generally requested through SQL targets and the outbox. Janitor does not rely on the adapter's parent-child resume mechanism for this pipeline. Committing a successor request alongside the producer's business writes makes that dependency recoverable from PostgreSQL even if the producer loses its reply. [70][23]

Schemas define the durable contract

Workflow.make declares the payload, successful result, expected error, and idempotency input. These values cross a storage boundary. The engine must be able to encode them now and decode them after a later deployment. A typed error describes a failure the program knows how to represent. A defect is a failure outside that expected error model; it still requires a deliberate recovery policy.

toLayer associates the definition with its implementation. The dispatcher has a separate registry that maps the SQL workflow tag to payload decoding and submission. Both registrations are necessary: one tells the dispatcher how to start work, and the other tells the engine which handler runs inside the execution object. Adding only one can leave requests unsubmitted or executions without a handler. [71][13]

Layers explain the large Worker initialization block

A Context service is a named dependency with a typed interface, such as WorkflowOutbox or GitHubTransport. A Layer describes how to construct that service from other services. Supplying a SQL layer allows the outbox layer to build; supplying the outbox and engine lets the dispatcher build. This is dependency construction, not the order in which PR events execute.

Layer.mergeAll combines services or registrations. Layer.provide supplies dependencies, and provideMerge also keeps the supplied services available to downstream consumers. ClusterWorker assembles one graph so HTTP routes, queue handling, maintenance, and workflows use the same service definitions. Tests can substitute a transport or engine without changing the business function.

The adapter builds that graph into an isolate-lifetime context. Services that need an event-specific resource must still acquire it in the appropriate event scope. Worker initialization also resolves secrets and resource bindings so Alchemy can discover the bindings during deployment; resolving them only deep inside a lazily built workflow layer would be too late for that discovery. [72][21]

04 / Durable runtime

What survives an isolate restart

The adapter saves activity exits under ${activity.name}/${attempt}. Both successful and failed completed activities can be replayed from storage. Code outside an Activity runs again. Activity names, payload/result schemas, and branching therefore form a compatibility contract across deployments. This is checkpointed execution, not an exactly-once guarantee for GitHub writes.

All DurableClock.sleep calls use storage on this adapter, including short waits: it supplies a zero in-memory threshold. Named clock rows are first-write-wins. An alarm records due deferred completions and resumes the execution. A persisted pending-resume flag and 60-second guard alarm cover lost deferred wakes. Cloudflare itself provides at-least-once alarm execution. [19][20]Cloudflare alarms

Durable storage still needs a wake

The adapter does not install a perpetual watchdog for every newly accepted execution. A run lost before a result or pending-resume flag is stored can need external contact. A terminal Complete result, including failure, is not rerun by resume. Janitor's sync recovery adds a business-level replacement-generation path, but only for sync workflows.

The cluster context lives for the isolate. cluster.provide attaches that context; it does not create a new Scope. The adapter removes the build memo map to avoid pinning handler-provided layers to a prior Cloudflare request context. Services should cache completed values carefully and avoid retaining request-owned I/O or unresolved promises across events. [21]

Replay restarts the program and reuses recorded answers

A workflow checkpoint is not a suspended JavaScript stack. On a later wake, the handler starts again. When it reaches an activity whose exit is already recorded, the engine returns that saved exit. When it reaches a missing activity, it executes the step. The handler can therefore reconstruct its progress from stable activity names and results.

For example, a refresh can save its issue response and PR response, then encounter a rate limit while reading reviews. Its durable clock records when it should resume. After the wake, the earlier fetch activities return their recorded responses and execution reaches the review attempt again. A successful earlier request does not need to consume API budget again just because a later request had to wait.

This also explains why plain database reads, current time, and branching outside activities deserve attention. If their answers change on replay, the program may reach a different set of named activities. A changing decision that must remain stable for one execution should be recorded, as the begin activity records the run claim. A safety check that must use current state belongs at the effect boundary where that safety matters.

Activity boundaries determine what can be repeated

If GitHub returns a response and the object saves the activity exit, replay can reuse it. If GitHub accepted a label write but the object disappeared before saving the exit, replay cannot know that from the checkpoint alone. It may issue the write again. This is why label application is expressed as a desired set difference and why SQL writes use unique keys or conditional updates.

There is a similar gap between a SQL commit and an activity checkpoint. RefreshEntity closes the internal SQL gap by committing the mirror, verification, and handoff together. An activity replay may still revisit that transaction, so the transaction must also behave correctly when its logical work already happened. A transaction gives atomicity within one database; idempotency makes a repeated logical operation safe.

A large activity records less orchestration detail but repeats more work if its last checkpoint is lost. Smaller activities preserve finer progress at the cost of more stored results and a larger deployment compatibility contract. Janitor uses per-request fetch activities and per-page apply activities for scans, but a larger apply activity for a complete label plan. The review findings describe the retry and locking costs of that latter choice. [73][74]

An alarm turns waiting into stored work

An in-memory sleep depends on the current process surviving. A durable sleep records a due time and a named completion signal. The adapter uses a durable deferred, a persisted promise-like result, to represent that signal. When the alarm fires, the runtime records completion of the due signal and resumes the workflow.

Cloudflare gives an object one alarm, so the adapter stores multiple named clocks in a table and arms the alarm for the earliest one. After servicing due clocks, it computes the next wake. The 60-second pending-resume guard addresses a narrower failure: a completion signal was recorded, but the resume that should consume it was lost. It is not a universal timeout for all work in the object. [75]

05 / Consistency boundary

The SQL-to-workflow handoff

The outbox puts the business change and the request to start work in one PostgreSQL transaction. The dispatcher crosses the remaining boundary afterward. If it loses the engine's response, it retries the same identity. The engine's first-payload-wins behavior makes that resubmission converge on the existing execution. This is the reason the payload for an existing execution key must remain unchanged. [10][22]

Suppose projection commits a sync target and then calls the workflow engine. If the Worker disappears between those actions, the target says work is pending but no execution was requested. Reversing the order creates a different problem: the workflow can start even if the database transaction later rolls back.

The outbox closes a specific two-system failure window

Record Question it answers Why another record does not answer it
Cloudflare Queue message What should the consumer receive or retry? It does not share a transaction with PostgreSQL, and an acknowledged message is no longer the durable record of the business operation.
Webhook journal Have we seen this delivery, and what happened to its projection? A journal row alone does not guarantee that the workflow engine was asked to project it.
SQL outbox row Which committed operation still needs submission? An accepted submission does not establish that execution finished.
Workflow activity checkpoint Which named step exits can be reused during replay? It cannot atomically commit a GitHub mutation or replace application-wide SQL coordination.

They can look like four copies of the same job. Each records a different promise. The Cloudflare Queue holds an event awaiting delivery. The journal records that Janitor received the delivery and how it projected it. The outbox records that a committed business operation requires a workflow. The execution checkpoint records how far that workflow has progressed.

The outbox closes the gap between changing business state and requesting work. It joins the caller's transaction. State / transition Mechanism What a failure means
Requested → due Unique key workflow_tag, execution_key; optional due_at. An untouched, unaccepted duplicate may bring its due time forward. Rollback removes both the business write and its new request.
Due → leased One SQL statement selects with FOR UPDATE SKIP LOCKED, claims up to four rows, and assigns a random fencing token and 60-second lease. Another dispatcher can reclaim after lease expiry.
Leased → accepted Schema decode, engine submit with 20-second timeout, then token-checked accepted_at update. If the engine accepts but SQL acknowledgement fails, resubmission targets the same execution.
Leased → retry Token-checked release with exponential delay. Unknown tags wait one hour. Per-row work has a 30-second timeout. A timed-out cleanup can leave the row leased until expiry. No terminal quarantine state exists.
Accepted → business complete Workflow-specific SQL records, distinct from the outbox. Accepted rows are excluded from dispatch. Completion and stalled-run recovery need another mechanism.

The dispatcher defaults to 100 claims per call with concurrency four. The singleton makes up to three passes and can sleep for a due item within the next five seconds. That short sleep is ordinary Effect.sleep; if it is lost, the next cron wake recovers it. [24][25]

A lease prevents abandoned ownership from lasting forever

A dispatcher claims a due row for a bounded period. It does not hold an open SQL transaction while waiting for the workflow submission response. Another dispatcher skips that leased row until the lease expires. The token identifies which claim may mark it accepted or release it.

For example, dispatcher A pauses long enough for its lease to expire. Dispatcher B acquires a new token and submits the request. If A eventually returns, its old token cannot overwrite B's outbox state. The lease bounds how long lost ownership blocks submission; the token rejects stale acknowledgements. The execution ID handles duplicate engine submissions, which can still occur across that boundary.

The immediate wake reduces ordinary latency. The minute cron supplies a later opportunity when an enqueue happened without a usable scope finalizer, a wake failed, or a process disappeared. Because the singleton ignores overlapping wakes while it is active, immediate notification is a best-effort acceleration of durable SQL work. The due row, rather than an in-memory notification, remains the source of pending submission. [76][77]

Follow the failure to the store that still owns work

Before queue acknowledgement, delivery retry belongs to Cloudflare Queues. After journal commit, projection progress belongs to the journal and its requested execution. Before outbox acceptance, the dispatcher can retry submission. After acceptance, execution recovery must inspect workflow state and the business record. After an external label call, the action record and GitHub state determine what remains uncertain.

This ownership transfer explains why a retry loop in one component does not repair every failure. The outbox cannot fix a terminal failed workflow simply by resubmitting its accepted key. The sync recovery service instead inspects accepted executions and can make their targets eligible for a new generation. Equivalent recovery is not yet implemented for every workflow type.

06 / Synchronization

Generations coalesce changes without losing follow-up work

A sync scope is app inventory, installation inventory, a repository track, or one issue/PR. sync_target is its durable coordination record. Invalidations advance the requested generation. A pending execution prevents a second concurrent submission for that target. At begin, the execution captures the latest request generation and event sequence; newer requests that arrive after begin become follow-up work.

Page writes use withRun to fence ownership in the same SQL transaction. Webhook sequences and source timestamps prevent stale observations from overwriting newer mirror state. Pagination has named fetch activities and apply activities; verified completion advances the relevant watermark. Targeted entity refresh atomically commits mirror data, target verification, and labeling handoff. Collection scans do not evaluate every item: trackVerified is a no-op in the labeling integration. They can request targeted repairs for missing details or absent open entities. [28][29]

A generation preserves invalidations that arrive during a scan

A single boolean such as needsSync cannot express whether an event arrived before or after a run captured its input. If a scan clears that boolean when it finishes, it can accidentally clear a newer request. Counters make that ordering visible. Completion records the generation it actually owned; if requestedGeneration is greater, there is follow-up work.

The immutable execution generation and the captured active generation solve a second problem. Debounce lets requests 1, 2, and 3 be covered by the execution originally queued for 1. Its workflow payload remains unchanged, satisfying first-payload-wins, while begin records that it owns work through 3. A replay of begin must return the same claim rather than silently adopting request 4.

The cost of debounce is intentional latency. A small burst produces fewer GitHub fetches, but the first event waits for the due time. Manual sync can bypass that delay because it expresses a foreground request for progress. Publishing a policy uses neither path: it changes configuration and intentionally schedules no scan. [26]

Observation, verification, and completeness are different

Applying page one of a scan makes useful observations available immediately. It does not prove that page two was fetched or that the entire track is current. Janitor publishes verification and advances the scan watermark only when traversal succeeds. If page five fails, the earlier page writes remain useful, but the scan cannot certify completeness.

The incremental watermark answers how far a successful update scan reached. The separate last-full timestamp answers when the application last repaired the complete open set. Keeping them separate stops frequent incremental successes from postponing full repair forever. Missing an item in a listing is treated cautiously: the application can request a targeted refresh rather than conclude that absence proves deletion.

Likewise, an ETag response validates one cached representation of one URL. It does not validate an entire paginated collection. The paginator follows page continuations and can probe beyond a previously full final cached page. These rules limit incorrect completeness claims even though GitHub pagination itself is not a transactionally frozen snapshot. [78][79]

Rate budgeting must be shared across executions

A limit kept in one Worker's memory would be incomplete as soon as another Worker isolate or workflow object made a request with the same credential. The SQL budget gives those callers a common place to reserve capacity and observe cooldowns. Short-lived leases also release reservations after a caller disappears.

Foreground work has access to a reserve that background scans leave unused. That trades some scan throughput for room to perform user-facing operations. A durable rate-limit wait is normal pending work, so the recovery service must not replace it merely because it is old. A recorded Suspended result and missing progress in a live run mean different things. [32][80]

07 / Labeling semantics

Publishing changes future evaluations immediately

Publishing a policy or editing enabled rules writes an immutable configuration snapshot and advances configured/active revision pointers in the transaction. It does not launch a scan or backfill. Work already queued and work created by later events or targeted background refreshes use the newest available configuration at the qualification checks. There is no issue-creation or webhook-arrival cutoff. [34][35]

Evaluation resolves published policy dependencies and enabled rules, derives facts from the mirror, and records a plan. Classifier policies use the optional AI provider and consent controls; unavailable classification yields unknown and preserves labels. Apply checks connection, repository enablement/access, configuration revision, and AI consent. It adds or removes individual labels rather than replacing the entire label set.

A reconciliation payload holds an identity, not a frozen copy of all facts. Evaluation reloads the mutable SQL mirror. SnapshotHandoff stores a fingerprint of selected fields, but that fingerprint is not a complete fact snapshot or an apply-time lock. Snapshot qualification and write fencing remain necessary. [38]

The apply step uses the SQL mirror's current labels to skip already-satisfied actions. It does not fetch a fresh GitHub label set first. A successful remove-404 is treated as already absent. An add-404 disables associated rules and advances configuration. The returned workflow outcome remains the evaluation outcome; inspect labeling_label_action for actual write success. [39]

Rules revisions make changing intent explicit

A policy draft is editable text. A published policy version is the saved program an evaluation can name. A rule binds a policy to a label action. A repository configuration revision collects its enabled rules and published dependencies. That revision gives one evaluation a consistent description of the intended behavior, even though the repository's configured pointer can later advance.

The snapshot generation and rules revision vary independently. The PR can change while the rule stays the same; the rule can change while the PR stays the same. Including both in the reconciliation identity prevents one result from silently standing in for the other. Keeping the published configuration allows the audit trail to explain an older decision.

The selected product behavior is that publication changes which configuration future evaluation checks use without initiating a backfill. This keeps publication bounded by saving configuration, rather than by repository size or GitHub API availability. An older queued event can still use the new revision. There is no event-time cutoff, and users should not expect every existing item to be relabeled just because they published. [81][36]

Synchronization supplies facts; labeling decides what they mean

The SyncIntegration interface is the deliberate connection between those concerns. Labeling tells refresh which collections the current configuration requires. When a targeted entity becomes verified, refresh invokes entityVerified, and the labeling implementation creates the reconciliation handoff.

This keeps GitHub pagination, freshness, and repair ownership in synchronization. The evaluator consumes the mirror and published policy definitions. A deterministic policy can be tested without making a GitHub call. Fetching only required collections saves requests, but it also creates the publication-overlap case described in the review: a newly published policy can require facts that an already-running refresh did not collect. [82][83]

Unknown preserves a distinction that false would erase

An unavailable review collection or a failed classifier does not establish that a rule is false. Treating missing evidence as a negative answer could remove a label for the wrong reason. The evaluator and plan preserve unknown as its own outcome so uncertainty does not automatically authorize destructive label changes.

The classifier returns a bounded decision through a provider interface. It does not receive the GitHub transport as a tool for choosing and making mutations. Consent, leases, caching, and the prompt contract live in the classifier service; the rule planner and apply step still control labels. This separates an uncertain external answer from authority to change a repository. The optional provider can be unavailable while deterministic evaluation continues. [84][85]

A label plan is a proposed delta, followed by an attempt

Replacing the entire remote label list would risk deleting unrelated labels added by a person or another integration. The implementation sends individual additions and removals and records an action per managed label. This bounds the mutation to the rule's intended output.

It still cannot atomically check and mutate GitHub. A person can change a PR or its labels after Janitor checks its local state. The existing repository row lock serializes disconnect against the application's write attempt; it does not lock GitHub. Further fencing, retries, and later observations are required to keep that uncertainty visible and restore agreement. Findings F04 and F05 identify where the current implementation needs stronger handling.

These queries are diagnostic examples for the inspected schema. They were not run against production. Start with backlog age and actual action outcomes, then inspect queue metrics and the relevant workflow execution. Avoid resetting keys or deleting checkpoints as a general retry technique.

PostgreSQL and object storage solve different query problems

The application needs to list all repositories, find overdue targets, share a rate budget, and inspect failed label actions. Keeping those records in separate workflow objects would require discovering and contacting many objects to answer a single page or maintenance query. PostgreSQL supplies relational queries and transactions across those business records.

The workflow runtime needs a smaller, execution-local record: the original payload, named step exits, pending signals, and clocks. The selected adapter puts that record next to the execution in Durable Object SQLite. PostgreSQL does not have to become the internal checkpoint schema for the engine. The cost is two persistence systems with separate backup, retention, and failure behavior.

Hyperdrive is the database connection path used by the Worker. Its query cache is explicitly disabled because stale reads would be incorrect for ownership, configuration, and progress checks. Reusing connections and reusing query answers are separate choices. The code records why it disables cached answers; it does not establish that Neon was chosen over every other PostgreSQL provider through a comparative benchmark. [86]

R2 handles payload size, and encryption spans the handoff

Large webhook bodies should not force the consumer to use a different business protocol. Ingress encrypts the body and sends either inline ciphertext or a reference to ciphertext in R2. The consumer resolves either representation into the same journal record. The size check applies before the event becomes workflow work.

R2 is temporary overflow storage, so the consumer deletes an object after journaling it. A lifecycle rule cleans up objects left by crashes or failed best-effort deletion. Payload encryption protects content as it passes through queues, overflow storage, and the journal; it is separate from the GitHub signature check, which establishes authenticity. It does not cover every decoded activity result stored by the workflow engine, which is why checkpoint retention is a separate review finding. [87][88]

Maintenance supplies another chance to make progress

Webhooks provide a prompt observation when they arrive and are mapped correctly. Scheduled synchronization covers missed observations and refreshes older tracked state. The outbox singleton retries requests that have not been accepted. Sync recovery inspects work already accepted by the engine. These are separate reasons for maintenance, even though one minute cron wakes both singleton objects.

A singleton prevents overlapping invocations of the same maintenance pass from running simultaneously in the object. It does not make every SQL write or workflow submission happen exactly once. A pass can be interrupted and revisited, so it still uses idempotent requests and database fences. The five-minute planner throttle also prevents every cron wake from creating a fresh inventory cycle.

Operationally, inspect the last point that definitely succeeded. If a policy saved but no existing PR changed, that can be the intended no-backfill behavior. If a webhook was accepted but its journal is absent, inspect delivery. If the outbox is accepted but the target never verifies, inspect execution recovery. If evaluation finished but GitHub has the wrong label, inspect action outcomes and the write path. A database-ready response cannot distinguish those cases.

The following comparisons explain the consequences of the implementation. They are architectural assessments, except where a cited project note records the decision. They are not historical claims that the team benchmarked and rejected each alternative.

Tradeoffs of the chosen design

The architecture has solid transaction boundaries, generation fencing for sync writes, bounded dispatcher concurrency, shared rate budgeting, and explicit revision handoff. The highest-priority changes are at the edges of those guarantees. Findings below come from source inspection; the failure interleavings are reasoned scenarios, not reproduced production incidents.

HighF01

Complete the event-to-refresh mapping

Issue changes are dropped at ingress. Check, status, and review events can be marked projected without creating work. A rule depending on a completed check or a new review may keep its old result until another event or repair causes a targeted refresh.

Evidence [11][12]

Recommended change. Add issue projection and targeted invalidation. Resolve PRs affected by review/check/status events and invalidate those targets with the delivery sequence. Preserve debounce and latest-revision semantics; publishing should still create no backfill.

Validation. Exercise each event through journal, projection, outbox, refresh, and reconciliation. Check that duplicate deliveries and shared commit SHAs produce bounded work.

HighF02

Wire retry exhaustion to the dead-letter queue

The application explicitly parks malformed or unrecoverable messages, but the queue consumer configuration omits deadLetterQueue. Persistent transient failures use message.retry and can exhaust the ten retries. Cloudflare documents that exhausted messages are deleted when no DLQ is configured. This finding concerns repository configuration; live dashboard drift was not inspected.

Evidence [44][45]Cloudflare DLQ behavior

Recommended change. Bind the existing dead-letter queue as the consumer's exhaustion destination. Add a replay/archive procedure that accepts both native exhausted envelopes and the application's diagnostic wrapper, with an alert before queue retention expires.

Validation. Force journaling to fail beyond the retry limit in a Cloudflare-compatible integration environment and verify the message reaches the DLQ.

HighF03

Recover accepted non-sync executions

The outbox stops dispatching accepted rows. recoverSyncExecutions covers only the four sync scope types. A projection, reconciliation, or test execution lost before it persists a result or a durable wake may remain unfinished. Reusing its accepted outbox row will not dispatch it again. A terminal failed execution also needs an explicit retry identity or repair operation.

Evidence [46][47][48]

Recommended change. Add an execution ledger/recovery registry for all seven workflow types. Distinguish running, suspended, terminal failure, and business completion. Resume interrupted storage-backed work and create an auditable new attempt for terminal failures, preserving delivery and label-action idempotency.

Validation. Evict after acceptance and before the first activity checkpoint. Also inject terminal SQL failure in projection and reconciliation. Verify eventual completion without requiring an unrelated webhook.

HighF04

Enforce the snapshot fence at label application

Evaluate checks the target's verified generation and freshness. applyPlan checks repository state and configuration, but does not re-read sync_target to enforce snapshot generation or freshness. A newer refresh can complete between evaluation and apply, allowing an older plan to write labels. The comment saying "snapshot not superseded" overstates the implemented check.

Evidence [49]

Recommended change. Requalify the target immediately before applying and hand off when its generation changed. Design per-entity serialization or an explicit action claim shared with snapshot updates. Keep the remote-write race explicit; SQL and GitHub do not share a transaction.

Validation. Pause after Evaluate, commit a newer verified snapshot with a different label plan, then resume Apply. Assert that the older plan performs no remote write.

MediumF05

Give label writes durable retry and explicit completion status

Sync fetches use withRateLimitWaits. ReconcileEntity/Apply directly calls GitHubTransport and maps transport or budget failures to an activity error. HTTP failures can be recorded as failed actions while the workflow still returns evaluated. No equivalent action retry loop is present.

Evidence [50][51]

Recommended change. Introduce bounded, durably named write attempts with rate-limit waits and per-action outcomes. Recheck desired state and safety conditions on every attempt, and expose evaluation and application status separately.

Validation. Inject rate limiting, a 5xx response, and a response lost after GitHub accepted a write. Verify eventual convergence and truthful user-visible status.

MediumF06

Set retention for workflow checkpoints and accepted requests

Activities store decoded GitHub response data in DO SQLite. ContentPurge clears selected SQL content but never deletes workflow checkpoints. The adapter has no completed-execution cleanup, and accepted outbox rows also have no general cleanup path. These stores grow and can retain content beyond the SQL purge window.

Evidence [17][52][53]

Recommended change. Define separate checkpoint, outbox, audit, and replay retention periods. Index executions by repository/installation for purge. Preserve deduplication tombstones where deleting a completed execution would otherwise allow old events to run again.

Validation. Complete a content-bearing workflow, trigger access-loss purge, and inspect both Neon and DO storage. Redeliver an old event after cleanup and verify it cannot recreate forbidden work.

MediumF07

Quarantine permanently invalid outbox requests

Unknown workflow tags are retried hourly. Payload decode failures are retried with the same backoff as transient engine failures, without a maximum attempt count or terminal status. Invalid records can remain permanent backlog.

Evidence [54]

Recommended change. Separate schema incompatibility from transient submission failure. Add a quarantined state, error metadata, and explicit replay after a compatible handler or migration is deployed.

Validation. Submit an unknown tag and an old incompatible payload. Verify they become actionable quarantined records while healthy rows continue dispatching.

MediumF08

Test replay against the deployed adapter

The repository's recovery tests use WorkflowEngine.layerMemory and simulate Cloudflare differences. Worker.test.ts verifies module construction. Those tests do not exercise actual SQLite checkpoints, alarm loss, singleton wakes, or Cloudflare request-context constraints.

A historical deployed spike did exercise clocks and replay across a Worker redeployment. That strengthens confidence in the pinned integration, but it is not a repeatable test of all current application workflows. [91]

Evidence [55][56]

Recommended change. Add an adapter contract suite under workerd or a staging deployment. Include restart/replay and old-payload compatibility fixtures. Keep old workflow handlers when introducing incompatible tags; checkpointed executions replay with the currently deployed implementation.

Validation. Run the same execution across an isolate restart and a deployment change. Cover completed activities, durable sleeps, parent resumes if introduced, and interrupted write attempts.

MediumF09

Measure repository-wide locks around remote writes

applyPlan holds a github_repository row lock inside a SQL transaction while issuing sequential GitHub requests. This deliberately serializes disconnect with writes, but also serializes label application across all issues in that repository and can delay a disconnect behind remote latency.

Evidence [57]

Recommended change. Measure lock wait time and transaction duration. If contention is material, replace the long repository lock with explicit short action claims and a disconnect-drain protocol that preserves the current safety intent.

Validation. Apply labels to several issues while delaying GitHub responses, then disconnect. Verify both bounded latency and the documented write/disconnect ordering.

One more revision race to cover

RefreshEntity checkpoints its required collection list. A policy published afterward can require checks, reviews, or changed files that the running refresh did not fetch. Latest-revision handoff alone does not hydrate those facts. Add a test for this interleaving and define whether it schedules a targeted refresh or reports unknown until the next qualifying event. [58]

What the original Cloudflare spike demonstrated

The project records a deployed experiment against the pinned adapter. Duplicate submissions returned the same execution ID and original result. The test crossed durable clocks, observed queue and cron work, and recovered from a Neon interruption after a fresh request without restarting the Worker.

It also redeployed while an execution was suspended on a two-minute clock. Later contact returned the same execution ID and completed result, with one recorded copy of each test commit. Earlier discarded executions had completed through alarm wake. These are useful observations of deployed replay and persistence, beyond what the in-memory test engine can establish.

The report explicitly says Cloudflare did not expose deterministic isolate eviction. The spike was retired on 5 September 2026. Treat it as evidence for the scenarios and pinned revision it tested, not as proof of every current workflow's failure handling or a continuously running production health check. The recommendation in F08 is to make these contracts repeatable for the present application. [90]

How to explain the architecture to another engineer

Begin with the job: turn GitHub changes into labels using published repository rules. Then explain that GitHub owns remote facts, PostgreSQL owns configuration and coordination, and the workflow object owns execution checkpoints. Follow one PR through acceptance, projection, verification, evaluation, and application.

For each handoff, name the receipt left behind and the component that will retry it. Finally, explain which guarantees stop at the database boundary. The outbox prevents a committed request from depending on one immediate engine call. Checkpoints preserve recorded step results. Neither can make a GitHub call atomic with local storage. The review findings show where the current system has not yet completed that recovery story.
