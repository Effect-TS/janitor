# Resolving review threads and minimizing review comments

## Findings

- `resolveReviewThread(input: ResolveReviewThreadInput!)` marks a review thread as resolved and returns its `PullRequestReviewThread`. Its required identifier is `threadId: ID!`, not a comment or review ID. The inverse operation is `unresolveReviewThread`. [Mutation](https://docs.github.com/en/graphql/reference/pulls#mutation-resolvereviewthread), [input](https://docs.github.com/en/graphql/reference/pulls#input-object-resolvereviewthreadinput), [inverse](https://docs.github.com/en/graphql/reference/pulls#mutation-unresolvereviewthread).
- The permission field is **`viewerCanResolve`**, not `canResolve`. The thread also exposes `viewerCanUnresolve`, `isResolved`, `resolvedBy`, `isOutdated`, and `isCollapsed`. Use the authenticated viewer's capability rather than inferring permission from comment authorship or repository access. The API reference describes the capability but does not give a complete role/token authorization matrix for this mutation. [Thread fields](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewthread).
- Minimization is supported by the documented schema for **both `PullRequestReview` and `PullRequestReviewComment`**, as well as `IssueComment`. An inline review comment is therefore not excluded merely because it is not an `IssueComment`. These are different node types: target the actual review/comment node ID, not the thread ID. [Minimizable implementors](https://docs.github.com/en/graphql/reference/issues#interface-minimizable), [review](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreview), [review comment](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewcomment), [issue comment](https://docs.github.com/en/graphql/reference/issues#object-issuecomment).
- `minimizeComment` accepts `subjectId: ID!` and `classifier: ReportedContentClassifiers!`. **`RESOLVED` is a valid classifier**, described as "The content has been resolved." The returned `minimizedComment` implements `Minimizable`; its `minimizedReason` uses lowercase `resolved`, unlike the uppercase mutation input. [Mutation](https://docs.github.com/en/graphql/reference/issues#mutation-minimizecomment), [input](https://docs.github.com/en/graphql/reference/issues#input-object-minimizecommentinput), [classifier](https://docs.github.com/en/graphql/reference/meta#enum-reportedcontentclassifiers), [result fields](https://docs.github.com/en/graphql/reference/issues#interface-minimizable).
- Schema support does not imply permission on every object. Query `viewerCanMinimize` and `isMinimized` for each intended target; `viewerCanUnminimize` and `unminimizeComment` cover reversal. Review-level minimization and comment-level minimization are distinct targets. The docs do not promise that minimizing a review recursively minimizes its inline comments. [Capabilities](https://docs.github.com/en/graphql/reference/issues#interface-minimizable), [inverse mutation](https://docs.github.com/en/graphql/reference/issues#mutation-unminimizecomment).

## Recommendation and limits

Keep thread resolution as the operation that records an addressed review conversation. Permission-aware minimization with `classifier: RESOLVED` is a supported additional operation on eligible review/comment nodes, not a replacement for resolution. Check `viewerCanMinimize && !isMinimized`, then inspect the mutation result; capability checks do not remove the need to handle mutation errors. This is an implementation recommendation based on the separate API operations above.

Do not equate `minimizedReason: "resolved"` with thread `isResolved`. Nor should an API integration promise that either operation hides every review surface in GitHub's UI. The thread reference describes `isCollapsed` as "Whether or not the thread has been collapsed (resolved)," while the minimization API promises comment minimization. These references do not specify rendering across the conversation timeline, review summaries, and file-diff views. No live mutation or UI verification was performed.

## Repository integration and regression coverage

Thread resolution already exists in `apps/cluster/src/PullRequestReview/GitHub.ts` (`resolveThread`) and `apps/cluster/src/PullRequestReview/Publish.ts`. The publisher selects open threads judged `addressed`, resolves them without a reply, and re-reads history to reconcile a lost response. Existing publisher tests cover both behaviors; the focused run passed both tests (22 other tests skipped).

For a subsequent implementation, extend fetched comment facts with `viewerCanMinimize` and `isMinimized`, and add a GitHub adapter operation using `minimizeComment` with `classifier: RESOLVED`. After successful resolution, minimize eligible Janitor-owned root comments in addressed threads. Include already-resolved addressed threads so a crash between resolution and minimization can recover. Use the existing durable publishing steps and re-read minimization state before retrying. Skip unauthorized or already-minimized comments; a minimization failure should not reverse resolution or prevent finalization. Never minimize human replies or an entire review containing still-standing findings.

Proposed test seam is the existing publisher integration harness with its fake GitHub transport. One focused scenario should show an addressed thread becoming resolved and its eligible Janitor root comment minimized as resolved, while a still-standing thread and human replies stay untouched. This exercises the real adapter and publisher together. Repository TDD instructions require explicit seam confirmation before adding tests; no new test was written pending that confirmation. Implementation remains deferred as requested.
