# Private Slack conversations

Start with [app-manifest.json](app-manifest.json), replacing `YOUR_JANITOR_HOST` with the deployment hostname. Merge these bot settings into the app used for account linking. User OpenID Connect grants remain separate from the bot grants. Reinstall the app after changing scopes and invite its bot to each private channel that will host conversations.

Set `JANITOR_SLACK_WORKSPACE_ID`, `JANITOR_SLACK_APP_ID`, `JANITOR_SLACK_BOT_USER_ID`, `JANITOR_SLACK_BOT_TOKEN` and `JANITOR_SLACK_SIGNING_SECRET` for that installation. The singular workspace ID must also appear in the account-linking `JANITOR_SLACK_WORKSPACE_IDS` allowlist. Set `JANITOR_AGENT_RUNNER_URL` to the deployed agent runner's base URL and `JANITOR_AGENT_RUNNER_TOKEN` to the shared service secret. The agent runner must have the same token. Slack intake is enabled only when all bot settings and the runner settings are present. Deploy migration `0024_slack_conversations.sql` with the application.

Event Subscriptions points to `/api/v1/webhooks/slack`. Its Access bypass covers only that exact path. The handler verifies the raw request signature and timestamp before saving receipts. Slack URL verification uses the same signing secret. The API acknowledges after the receipt and authorization transaction commits; initialization, runner calls and Slack publication run separately. The route has a 2.5-second deadline and returns a retryable failure if it cannot commit in time. Slack expects acknowledgment within three seconds, so monitor database latency and failed receipt responses. See [Slack request signing](https://docs.slack.dev/authentication/verifying-requests-from-slack/) and [Events API](https://docs.slack.dev/apis/events-api/).

Two teammates sign in to Janitor and connect their Slack accounts. One mentions the bot with `owner/repository`, an issue URL or a PR URL. A mention in an existing thread freezes only that discussion through the initiating message. A channel-root mention starts a new thread. Janitor asks for a connected repository when selection is ambiguous and saves replies while context or repository readiness is pending. Once established, ordinary thread replies are instructions, including replies sent during execution. A PR already bound elsewhere redirects to its existing home thread.

The minute cron services saved initialization and publication obligations. Active event reads use a thirty-second cadence; idle publication checks use five minutes. Channel sends are spaced by at least one second and honor Retry-After. Pending progress can coalesce, but substantive replies and errors retain their order. Output markers live in message metadata. Uncertain sends are read back through paginated thread history; only a matching bot author, home thread and marker confirm publication. An absent or deleted marker leaves the output held. Later output waits behind it. See [thread pagination](https://docs.slack.dev/reference/methods/conversations.replies/) and [Slack rate limits](https://docs.slack.dev/apis/web-api/rate-limits/).

`SlackConversation.inspect` reports thread initialization and frozen contributions. `SlackDelivery.inspect` reports pending or uncertain publication and its error. These service reads are available for later dashboard integration. Membership loss preserves the thread and pending output; delivery retries the same destination. Unlinked users receive best-effort ephemeral account-link guidance. There is no public fallback if ephemeral delivery fails.

## Validation and live evidence

Run `vp test apps/cluster/test/Slack` for Postgres-backed conversation/delivery tests and controlled Slack HTTP responses. The conversation test drives the existing ordered runner handoff with an admission response lost after the runner stores the input. The production transport and cron are wired into the Worker, but these tests do not establish live Slack installation behavior or real-provider behavior.

For a live check, use a separately installed test app, one explicitly designated private channel and two linked test teammates. Record the app, workspace, channel and root message IDs before starting. Limit the check to one conversation and its replies. Verify a mention, an ordinary reply during work, a substantive answer and one updating progress message. Confirm the configured scopes in the installation before running. Delete the test thread and disable the test app's Event Subscriptions when finished; remove temporary credentials and any test deployment resources. Do not reuse disposable fixture destinations as application defaults.

The five-minute scan for Slack messages missed by the receiver belongs to ticket 10. This slice retries received contributions and publication obligations; it does not claim to recover never-received mentions or deleted messages. Repository tools and remote workspace execution belong to later tickets.
