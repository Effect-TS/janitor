## Receiver and evidence requirements

Verify signatures over raw bytes before decoding. Persist provider delivery ID, event type/action, receipt time, raw payload hash, normalized identity, and acknowledgment result. Keep raw private payloads only in restricted temporary fixture storage; public results contain synthetic text, IDs, checks, and hashes. Never log headers carrying credentials. Invalid signatures and stale Slack timestamps must not enter the journal. A valid receipt commits before its success acknowledgment; processing can continue asynchronously.

Provide modes for returning a controlled failure before persistence, committing then losing the acknowledgment, delaying processing, and holding/reordering captured events. Replay captured events inside the local processor without forging new platform requests. Record transport retry behavior separately from deterministic replay behavior. Keep admission decisions and output intent/projection updates transactional. Membership changes and final acceptance need a shared linearization point, not a cached eligibility lookup followed by an unrelated commit.

Every executed scenario records run ID, script/source hash, granted permissions, installation identity, provider receipt IDs, normalized input IDs, acceptance sequence, marker/remote output IDs, and assertions. Distinguish observed, locally simulated, documented, and unverified. The live fixture is disposable test code and does not establish that the production adapter exists.

## Slack checks

1. Confirm token identity, private conversation metadata, bot membership, and `conversations.replies` access using the granted bot scopes. Use two-result pages and read metadata back. Public-channel routing must reject even if the bot can observe the event; do not infer privacy from the channel ID prefix.
2. Create a root with preceding human context, mention the bot in a later reply, and send more replies while initialization is held. Capture both mention/message deliveries. Query only that root through the initiating `ts`, page completely, freeze attributed context, and admit the initiating message exactly once. Subsequent authorized replies are ordinary inputs without another mention. Unrelated roots and pre-session context must never become inputs.
3. Deliver duplicates before and after teammate removal/restoration. Preserve the first accepted payload and rejection. Distinct same-text messages stay distinct. Test original/edit/delete envelopes in both orders; mutation receipts must not occupy the original message's admission identity. Own posts and other bot posts create no turns.
4. Fail an acknowledgment, inspect actual retry headers and receipt identity, then reconcile a deliberately omitted visible reply via history. Persist boundary and scan status across receiver restart. Repeat with deleted and edited messages and a wholly missed first mention. Report these as unrecoverable or changed-history cases, never successful lossless recovery.
5. Publish a reply with metadata containing a random operation ID and part index. Lose its successful response locally; find it through all history pages with `include_all_metadata=true`. Validate app author, workspace, channel, root, operation ID, and part. Hold lookup results to simulate visibility delay. Delete a fixture output before lookup and verify unresolved status with no repost. Metadata spoofed by another author must not confirm publication.
6. Coalesce progress while keeping final/error output and substantive sequence. Split oversized plain-text output at a documented conservative limit, persist each part's identity, and block later parts behind an unresolved earlier part. Rate scheduling is shared across sessions in a channel; honor retry timing and survive restart without a retry storm.
7. Attempt private onboarding while a participant is active/inactive and before/after replies exist. Human observation is required to establish visibility. An API success cannot establish receipt; do not fall back to thread clutter or unsolicited DMs.
8. Remove the bot from the test channel while output is pending, then restore it. Keep accepted work, retain outgoing text, report delivery access loss, and verify read/write membership before draining in order. Never redirect to another channel or DM.

## GitHub checks

1. Capture submitted reviews containing a body and multiple inline comments, including a review with no body, a body-only review, and a completely empty submission if GitHub permits it. Fetch review comments using two-result pages. Record IDs, review state, submitted time, comment author, `pull_request_review_id`, and `in_reply_to_id`.
2. Capture an individually published inline comment, a later reply to it, and a pending-review reply if supported. Establish which review events they produce. Replay each capture with review-first, comment-first, retries, delayed hydration, and missing-one-event delivery. The classifier must use durable source relationships, not elapsed time or arrival order. Do not finalize grouping until these relationships are observed.
3. Freeze one normalized contribution and its covered comment IDs atomically. Retry after editing a comment and during multi-page hydration. Detect that pages are not a historical snapshot; an original version deleted before any receipt may be unavailable. Record the earliest captured version separately from later current API state. If exact grouping or content completeness cannot be proved, return the narrowed guarantee to the delivery decision instead of inventing a debounce.
4. Verify later standalone replies are not swallowed by a previously consumed review ID. Verify grouped inline comments do not create extra turns. Empty submissions must not cause an empty model invocation. General PR comments need an explicit mention; other issues and unrelated PRs must not create sessions. App-authored responses cannot feed back into input.
5. Force one disposable App webhook failure, enumerate and retrieve the delivery using an App JWT, and re-ingest through the same receipt and admission path. Compare duplicate redelivery GUID/attempt identities and preserve immutable decisions. Confirm permission errors, pagination, and scan progress without editing production App configuration.
6. Publish an inline reply and a PR-level response, each with an HTML-comment operation marker. Lose the response after the write succeeds; page the appropriate comments endpoint and match author, repository/PR, reply parent where relevant, and marker/part. Test deletion, missing reply target, delayed visibility, and duplicate marker. No negative lookup authorizes an automatic repost. A known missing target can use an explicitly attributed PR-level reply only after absence of an in-flight publication is established.

## Proposed recovery defaults, awaiting acceptance

These are test candidates, not amendments to the accepted contract.

- Slack: scan each known session's home thread every five minutes while it is eligible for delivery. Continue for waiting/idle sessions too, because a missed new message could be their only wakeup. Page retained replies after the session-start boundary with a ten-minute overlap from the last completed scan. Never advance on a partial scan. Rate limits may lengthen the interval; persist overdue coverage. Previously accepted/rejected identities are no-ops. Initial context is never intake. Enable optional Delayed Events if the test workspace supports it.
- Slack history is bounded recovery. Edits found without an original receipt must not silently become new instructions. Deleted messages and never-received start mentions cannot be reconstructed. Show a dashboard warning for detected outages or failed/overdue scans, and a concise thread notice once delivery is restored when a known gap needs human attention. Some silent losses cannot be detected. Ask users to resend a missed start; do not import arbitrary channel history.
- GitHub: every five minutes, start from the newest delivery page and follow opaque next cursors across the full retained three-day window. Persist an interrupted traversal, finish it, then rescan from the head. Inspect all statuses so transport failures without an HTTP status are not omitted. Deduplicate attempts by delivery GUID against durable intake and rejection records. Request redelivery for missing intake so the original signed webhook passes through the existing verifier; do not reserialize a retrieved JSON payload and present it as signed bytes. Full-window overlap is a conservative MVP candidate whose rate cost needs measurement. Warn on overdue scans and outstanding deliveries before retention expires; expired history cannot be claimed recovered. Scope any retrieved delivery details to the fixture installation/repository. A recovered event with no prior decision uses current authorization. Accepted/rejected events retain their original outcome.
- Uncertain output: repeated read-only reconciliation can establish a unique positive match. If it cannot, retain a visible unresolved delivery state and block that ordered output stream. Do not claim exactly-once delivery or retry simply because a timeout expired. Detailed recovery controls are a later product decision if this path needs them.
