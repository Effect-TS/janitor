# Durable Object capabilities for Janitor

Research date: 2026-09-11. This is documentation and source inspection, not an executed compatibility test or a hosting decision.

OpenCode V2 has a real Workerd profile that runs its core inside a Durable Object. The profile uses DO SQLite and durable event recovery. It deliberately replaces local repository and process services. A DO-hosted agent loop therefore has source support; a complete repository-editing agent still needs an execution environment behind those services. This distinction comes from the implementation, not assumptions about the CLI. See the pinned [ServerWorkerd implementation](https://github.com/anomalyco/opencode/blob/2df00955cb933e977427535d2505e50cbc689c69/packages/server/src/workerd.ts) and [Cloudflare SDK guide](https://opencode.ai/v2/docs/build/sdk/cloudflare/).

| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JavaScript and Effect execution            | Workers supplies web APIs and a subset of Node APIs. Some imports are only stubs. Recent compatibility dates enable Node compatibility by default. | Embedded OpenCode Effect API               | `OpenCodeWorkerd.create` and `layer` use the Workerd replacement graph and injected storage. | Filesystem                                 | `node:fs` exposes read-only `/bundle` and memory-backed `/tmp`, unique to each request. Temporary files count against memory. Watching and permissions are unsupported. [Filesystem](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)                                                                                                                                                                                               | This is not a durable checkout shared across turns. OpenCode's Workerd profile instead marks its location filesystem and search services unavailable until backed by a remote environment.                                               |
| Shell, Git CLI, subprocesses and terminals | `node:child_process` is a nonfunctional stub. OpenCode replaces process spawning with `EnvironmentUnavailable`; PTY creation fails and VCS/snapshots return no-op results. [Node compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/), [Workerd profile](https://github.com/anomalyco/opencode/blob/2df00955cb933e977427535d2505e50cbc689c69/packages/server/src/workerd.ts)                                                | Unmodified local coding tools cannot run directly in the DO. This does not rule out remote tools or other implementations.                                                                                                               |
| Durable database                           | DO storage provides private, strongly consistent SQLite through `ctx.storage.sql`, with storage transactions. [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)                                                                                                                                                                                                                                                 | Use an adapter to that API, not a filesystem database path. `node:sqlite` is an import-only stub.                                                                                                                                        |
| OpenCode database adaptation               | Its Workerd SQLite adapter uses native DO transactions, rejects nested transactions, normalizes blobs, and bypasses unsupported tuning pragmas. [Adapter](https://github.com/anomalyco/opencode/blob/2df00955cb933e977427535d2505e50cbc689c69/packages/core/src/database/sqlite.workerd.ts)                                                                                                                                                           | The database adaptation exists. Janitor still needs schema ownership and migration boundaries, especially if sharing DO storage with Effect cluster tables.                                                                              |
| Long model calls and streams               | DO RPC/HTTP has no fixed wall-time cap while the caller stays connected. Active CPU defaults to 30 seconds and can be configured to 5 minutes; alarm invocations have a 15-minute wall limit. [Limits](https://developers.cloudflare.com/durable-objects/platform/limits/)                                                                                                                                                                            | Waiting for a provider is different from consuming CPU. Neither unlimited wall time nor a stream promises uninterrupted execution across deployments.                                                                                    |
| Background work after acknowledgement      | DO `waitUntil` has no lifetime effect. The lifecycle guide specifically says plain outbound fetch requests do not independently keep the object alive, including streaming response bodies. Outbound TCP/WebSocket connections postpone eviction for at most 15 minutes. [State API](https://developers.cloudflare.com/durable-objects/api/state/), [Lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/) | Do not treat a detached Effect fiber or provider stream as a durable job. Test the precise acknowledgement, drain, wake-up and replay contract.                                                                                          |
| Event concurrency                          | `blockConcurrencyWhile` gates startup and has a 30-second timeout. Ordinary async handlers can interleave. [State API](https://developers.cloudflare.com/durable-objects/api/state/), [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)                                                                                                                                                                         | Keep startup bounded. A shared object identity alone does not serialize every turn or make external effects atomic.                                                                                                                      |
| Restart and eviction                       | In-memory state is discarded and constructors rerun on activation. Deployments and platform changes can restart objects. [Lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)                                                                                                                                                                                                                            | Durable records must describe recoverable work. OpenCode forces event persistence and documents boot-time orphan-turn replay in its Workerd profile; test side effects and wake-up behavior rather than assuming exactly-once execution. |
| Scheduled recovery                         | One alarm per object, at-least-once delivery, with up to six automatic retries and exponential backoff. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)                                                                                                                                                                                                                                                                       | An application can multiplex scheduled work from durable records. Recovery must tolerate repeated delivery.                                                                                                                              |
| Outbound services                          | Fetch and streams support network APIs; DO limits list six simultaneous outbound connections per request. [Node compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/), [Limits](https://developers.cloudflare.com/durable-objects/platform/limits/)                                                                                                                                                                          | Model, Slack, GitHub and execution-service calls are plausible. Bound concurrency and verify the actual client/provider implementation.                                                                                                  |
| Observation connections                    | DOs support HTTP response streams and WebSockets. Hibernation WebSockets retain connections while resetting in-memory state. [WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [Limits](https://developers.cloudflare.com/durable-objects/platform/limits/)                                                                                                                                                 | A live dashboard connection is possible, but cannot be a requirement for keeping an unattended agent alive.                                                                                                                              |

The limits and lifecycle pages use different language for pending I/O. The former describes a connected inbound request; the latter explicitly excludes a plain outbound fetch as an independent keepalive. A feasibility test should exercise the intended return-early path rather than generalizing from a long-lived inbound stream.

## Existing Janitor runtime

[Worker.ts](../../../apps/cluster/src/Worker.ts) already calls `AlchemyCloudflareCluster.make`. It sets production compatibility date `2026-09-05`, local date `2026-07-04`, and `nodejs_compat`. Those dates differ intentionally because the local workerd is pinned. Local success alone cannot establish production parity.

The installed `AlchemyCloudflareCluster.ts` registers `ClusterEntity`, `ClusterWorkflow`, `ClusterDurableQueue`, and `ClusterSingleton`, with SQLite migrations owned by Alchemy. `CloudflareDurableObjectPrograms.ts` uses `state.storage.sql`, persists execution records, and rearms alarms from stored work during activation. These are existing integration mechanisms to evaluate, not a reason to build another scheduler by default. The source also forwards `waitUntil`; current Cloudflare documentation does not give that call durability semantics.

Local source references: `apps/cluster/node_modules/@effect/platform-cloudflare/src/AlchemyCloudflareCluster.ts` and `apps/cluster/node_modules/@effect/platform-cloudflare/src/CloudflareDurableObjectPrograms.ts`, supplied by the Effect pin above. This research inspected their declarations and recovery hooks; it did not audit their full delivery guarantees.

## Execution companions to evaluate

Cloudflare Sandbox SDK provides a concrete companion for shell, Git and filesystem operations. Its architecture routes Worker calls through a Sandbox Durable Object to a Linux container. The code executes in the container, while the DO supplies identity and lifecycle management. [Sandbox architecture](https://developers.cloudflare.com/sandbox/concepts/architecture/)

The stable Sandbox SDK documentation says files, processes and shell state survive while the container is active, then disappear when it stops. Reusing a sandbox ID starts a fresh container after sleep; identity is not persistent disk. The default inactivity timeout is ten minutes. Checkpointing or recreating a checkout, recovering unpushed edits, and reconnecting execution handles therefore remain design work. [Sandbox lifecycle](https://developers.cloudflare.com/sandbox/concepts/sandboxes/)

This companion could host repository tools behind a DO-hosted loop, or a broader runtime if later evidence favors that boundary. The OpenCode-to-companion adapter contract has not been established here. No architecture is selected by this research.

## Evidence still needed before implementation

- Bundle the exact OpenCode Workerd Effect entrypoint with Janitor's Alchemy toolchain and pinned Effect dependencies, confirming the `workerd` export condition and startup migrations.
- Establish how remote filesystem, search, process and VCS services attach through supported OpenCode APIs. Demonstrate a repository edit and validation with a controlled fixture.
- Test acknowledgement followed by unattended work, eviction mid-turn, the next wake-up, repeated delivery, and recovery around an external write. OpenCode history replay does not by itself prove that Git pushes or messages happen once.
- Decide which component owns session identity, tables, recovery alarms, workspace durability and status projection after these checks. Reuse the current cluster where its verified contracts fit.

These are future decision/prototype inputs. The current result establishes documented capabilities and source boundaries only.
